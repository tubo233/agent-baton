# Baton：多代理分工（中控）

**你，也就是调用本 skill 的这个会话，就是中控。**不管你是 Claude Code、Codex、Antigravity、Grok 还是别的代理，做法都一样：

- 中控负责想清楚、拆分、选人、出方案、等用户确认、派活、跟进、验收、汇报。
- 执行交给别的代理的无头进程，或者你自己的子代理。

两条底线：

1. **先拿出一份用户一眼能看懂的分工方案，等用户点头再动手。**
2. **交出去的每一件事都有验收办法**，不以"代理说做完了"为准。

本次任务：$ARGUMENTS
（如果上面没有被替换成具体内容，任务就是用户调用时附带的话；没有附带，就是当前对话里正在讨论的事。）

> **如果你是被派出来的执行方**（启动提示或任务书里写着你是执行方），不要使用本 skill，也不要再把任务派给别的代理，照任务书做完即可。

本 skill 的文件：
- `scripts/scan_agents.py`：扫描代理和模型；
- `scripts/dispatch.py`：建任务、派活、查进度、等待、停止、记验收；
- `scripts/agent_catalog.json`：各代理的启动模板；
- `references/`：各类说明；
- `local/`：个人配置。

脚本只用 Python 3.9+ 标准库。下文的 `<skill>` 指本文件所在的目录。

## 第零步：读配置和规则（只读）

1. **个人配置：**`<skill>/local/本机配置.md` 和 `<skill>/local/profile.json`，有就先读。里面的路径、代理端口、数据边界、额度和分工偏好，优先于本文件的默认做法。
2. **项目规则：**`AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`README.md` 等，确认数据边界、目录约定和输出位置。
3. **宿主说明：**在 [references/hosts.md](references/hosts.md) 里找到你自己那一节，了解这几件事：
   - 怎么向用户提问；
   - 怎么后台运行命令、怎么得知完成；
   - 有没有自带子代理；
   - 沙箱会挡住什么。

## 第一步：扫描本机的代理和模型（默认每次都做）

```
python <skill>/scripts/scan_agents.py --host <你自己的 id：claude / codex / agy / grok / ...>
```

- 约半分钟。它会：
  - 找出装了哪些代理，记下版本和可用模型；
  - 标出无头调用是"已实测"还是"按文档"；
  - 标出未登录、没有模型之类的问题；
  - 顺带报告榜单缓存的日期，以及本机战绩。
- 结果写进状态目录（默认 `~/.baton/`）里的 `inventory.json` 和 `inventory.md`。
- **沙箱禁网的宿主**（如 Codex 的 workspace-write）：
  - 列模型的命令要联网，要申请在沙箱外运行这条命令；
  - 不便申请时加 `--quick`：只找程序和版本，模型列表沿用上次的扫描。
  - 用户要求不改任何文件时，加 `--no-write`：只打印，不写清单。
- **完全不能运行命令时**（比如无人值守、终端被禁）：读状态目录里最近一次的 `inventory.md`，在方案里注明"沿用某月某日的扫描结果"。
- **清单处理：**
  - 没装、没登录、没有可用模型、被个人配置停用的代理，不进候选；
  - 你自己也在清单里。派给自己的模型有两种办法：用自带子代理（便宜，能直接回报），或另起一个无头进程。

## 第二步：查榜单

- **能跳过的情况：**缓存不超过 7 天，并且本机没有缓存里缺的模型。这时直接用缓存，在方案里写明日期。
- **其余情况：**按 [references/leaderboards.md](references/leaderboards.md) 查。
  - 用你自己的联网搜索；
  - 你不能联网，就把"查榜单"列进分工方案，交给能联网的代理，或请用户同意先用缓存；
  - 查完写回 `<状态目录>/leaderboard.json`。
- **规矩：**
  - 分数一律写来源和日期，不凭印象编；
  - 本机模型对不上榜单条目的，写"暂无榜单数据"；
  - 榜单测的是模型，同一模型装在不同代理里表现会不同，要和本机战绩一起看。

## 第三步：弄清任务（只读，不启动任何代理）

- **现状：**已经做过哪些、缺口在哪。
- **拆成工作项：**每项能单独交付、单独验收。判断性的问题和措辞定稿留给中控。
- **依赖：**哪些能并行，哪些要等别的结果。改同一批文件的工作不能并行给两个写手。
- **工作量：**估一下每项的工作量和要读的材料量。长文档、整库文献、大段代码要标出来。
- **不清楚的地方：**
  - 不问就**拆不出**方案的，先单独问一轮；
  - 其余并进方案的"需要你决定的"，并写明默认做法。

## 第四步：选人

按工种挑候选，再用榜单、本机战绩、额度和能力限制排序。工种和对应的榜单指标见 [references/leaderboards.md](references/leaderboards.md#按工种看什么)，各代理的特点和坑见 [references/agents.md](references/agents.md)。

| 工作类型 | 优先看 | 通常交给 |
|---|---|---|
| 写代码、跑实验、数据管线、测试、需要跑命令的转换 | 编码和终端类基准；无头时能否跑命令 | 编码榜靠前、有额度的编码代理 |
| 通读长文档、对照原文核内容、筛文献 | 长上下文基准、幻觉率 | 长上下文强的模型；输入由中控先抽成文本 |
| 联网取回或核对（论文、网页、规则、书目） | 检索类基准；有无自带搜索 | 自带联网搜索的代理 |
| 机械改动（字段、排版、重编号） | 速度、价格 | 便宜快的模型 |
| 交叉核对 | 和写的那方不是同一厂商 | 另一家厂商的模型 |
| 拆分、设计、判断、结果含义、给人看的说明、最终措辞、抽查、整合 | —— | 中控自己，不外包 |

还要考虑：

- **太小的活不外包。**写任务书、启动、验收的成本超过活本身的（比如十处以内的改动、一次编译），中控自己做。
- **额度。**写进方案的只能是已知情况：个人配置里写的、用户说的、报错里看到的。不要为了测额度去调用高级模型。
- **能不能跑命令、能不能联网。**按扫描结果和 agents.md 判断；没验证过的，一律按"不能"处理。
- **深查和抽查。**
  - 必须深查：要对外发布的数字和事实（包括书目信息）、要发到外部的内容、涉及受保护数据的运行。做法是用脚本全量比对原始来源，脚本做不了的逐条打开看。
  - 其余信任代理的自查，抽查即可。
- **备选。**每项写一个备选（主选额度用完或连不上时换谁）。方案里列了备选，换人就不用再问。
- **首次使用的代理**（扫描结果是"按文档，未实测"）：先派一个小试，确认跑得通再派正活。

## 第五步：提出分工方案，等用户确认

用通俗的话写，不出现内部编号和代号。模型名这类必要的技术词，第一次出现时加半句解释。

解释要有依据，比如榜单分数、官方说明、本机战绩。不要凭名字猜一个模型的定位，没依据就只写名字。曾有中控把榜单 50 分的大模型说成"轻量模型"。

照这个结构：

```
## 拟定分工

**任务：**一句话说明要完成什么。

**现状与范围：**已经有什么，缺口在哪，这次做到哪为止。

**本机可用：**扫描到的代理和主要模型（一行一个）；榜单数据的来源和日期。

| # | 工作项 | 交给谁（模型，档位） | 为什么选它 | 备选 | 交付什么 | 怎么验收 | 依赖 |
|---|---|---|---|---|---|---|---|
| 1 | …… | Codex（gpt-x，high） | 编码榜第 N（来源，日期）；本机 5 次 5 次通过 | Claude Code（sonnet） | …… | 测试 0 失败；我抽 5 个数核对 | 无，可并行 |
| 2 | …… | 我自己 | 需要判断和定稿 | —— | …… | —— | 等 1 |

**额度与成本：**各代理大概用多少、多长时间，已知的额度情况。
**数据边界：**各代理能读写哪里，明确禁止什么。
**下载清单：**会下载哪些文件（类型或文件名、来源、大致大小），存到哪里；不下载就写"无"。
**需要你决定的：**每条写明默认做法，例如"提交到 git：默认不提交，等你说"。没有就写"无"。
```

完整示例见 [references/example-proposal.md](references/example-proposal.md)。

然后停下来等确认：

- **提问方式：**用你这个宿主的提问工具，问"按这个分工开始吗？"，给"按此分工开始""我要调整"两个选项。没有提问工具，就在消息末尾直接问，然后结束这一轮。见 hosts.md。
- **在计划模式里**（例如 Claude Code 的 plan 模式）：
  - 把"拟定分工"整节写进计划，用户批准计划就等于批准分工；
  - 批准后不要再为这些步骤另开会话。
- **同意的范围：**用户同意方案，就算同意了"下载清单"里的下载、"需要你决定的"各项的默认做法，以及表里的备选。用户另有交代的，以交代为准。
- **用户改了分工：**重写那张表，再确认一次。
- **得到明确同意之前：**不建任务文件夹，不启动任何代理。

## 第六步：建任务文件夹，写任务书

- **方案存档：**把批准的方案存成 `<任务根目录>/<日期>_<任务名>_分工方案.md`。
  - 任务根目录：个人配置里的 `job_root`，默认 `<状态目录>/jobs`。
  - 以后换一个代理接着当中控，先读这份方案，再跑 `dispatch.py status`，就能接上。
- **每项外派工作一个文件夹：**
  ```
  python <skill>/scripts/dispatch.py new-job --name <任务名>
  ```
  - 它会建 `<任务根目录>/<日期>_<任务名>/` 和 `输入/`。
  - 代理的任务书、日志、报告、中间文件都放这里。
  - 需要改项目文件的，在方案和任务书里写明它的可写目录，其余位置只读或禁止。
- **输入预先准备好：**复制或抽取到 `输入/`。阅读类任务先把 PDF 按页抽成文本，并加上页码标记。
- **写两份文件**，模板和写法要点见 [references/brief-template.md](references/brief-template.md)：
  - `任务书.md`：完整规格；
  - `启动提示.md`：几行话，指向任务书。
  - 启动提示里必须写明三点："你是执行方""不要使用 baton skill""不要再把任务派给其他代理"。
- **任务书写到执行方不用提问：**
  - 范围、步骤、输出格式；
  - 可读可写的位置和禁止事项；
  - 遇到含糊时怎么办（自己决定、记进报告、继续做完）；
  - 最后的自查步骤。

## 第七步：派活与跟进

```
python <skill>/scripts/dispatch.py run --job <任务文件夹> --agent <id> --model <模型> [--effort <档位>] \
    [--access job|workspace|job_shell] [--workdir <可写目录>] [--add-dir <要读的目录>] [--offline] [--task-type <工种>]
```

- **命令怎么拼出来：**按 `agent_catalog.json` 的模板拼，再加上个人配置里的额外参数（例如禁用浏览器工具、额外可读目录）。
  - 个人配置里的禁止目录会被拒绝启动。
  - 想先看命令，加 `--dry-run`。
- **`--access` 的三个取值：**
  - `job`：只在任务文件夹里干活；
  - `workspace`：还能改 `--workdir`；
  - `job_shell`：允许跑终端命令，目前只对 Antigravity 有区别，要用户同意。
- **互不依赖的工作项一次全部发出。**
- **等结果，按宿主选一种**（hosts.md 有细节）：
  - 宿主能在后台命令结束时通知你（如 Claude Code）：把 `dispatch.py run ... --foreground` 作为后台命令运行，完成时会收到通知。
  - 其他宿主：`run` 会把任务放到后台、立刻返回；之后用 `dispatch.py wait --root <任务根目录> --timeout 3000` 阻塞等待（单次不超过宿主命令的时限），或等用户回来时跑 `dispatch.py status`。
  - 启动后确认一次状态是 running。之后不要反复轮询。
- **失败处理：**`status` 的"提示"一栏是从日志猜的原因，结论要看日志。
  - 额度或限流：换方案里的备选，按原任务书重派；
  - 临时故障：重试一次；
  - 登录问题：请用户处理；
  - 沙箱权限：改参数再派；
  - 同一项最多重派两次，再不行就告诉用户。
- **用户中途改主意：**
  - `dispatch.py stop --job <文件夹>` 连子进程一起停；
  - 把旧任务的半成品挪开或删掉；
  - 再按新分工重派。
- **等待期间**，做分给你自己的工作项。

## 第八步：验收、整合、汇报

- **先读代理的报告和自查**，再按方案里的验收方式核对：
  - 数字和书目：脚本全量比对；
  - 引用：抽几条，对照原文页面；
  - 代码：跑测试；
  - 图：打开看一遍。
- **记下验收结果：**`dispatch.py review --job <文件夹> --accepted yes|no --note "<一句话>"`。它会进入本机战绩，下次选人时参考。
- **对不上时：**代理报告"和给定值对不上"的地方，以原始结果为准，不迁就。
- **权限不够时：**代理因权限做不成的事（比如沙箱里写不了 `.git`），不要绕过限制。由中控按正常权限完成，或说明后交给用户。
- **提交到 git：**只在用户要求，或已批准的方案里写明要提交时才做。
- **汇报：**最后用用户的语言汇报：
  - 谁做了什么；
  - 你查了什么、发现并改了什么；
  - 还有什么没完成或没核实；
  - 产出放在哪里。

## 记下新经验

- 发现了新的命令写法、权限问题、额度变化或代理的新毛病：
  - 通用的写进 `references/agents.md` 或 `scripts/agent_catalog.json`；
  - 只和这台机器有关的，写进 `local/本机配置.md`。
- 某个代理第一次真实跑通：把 `agent_catalog.json` 里它的 `headless.status` 改成 `verified`，并写明日期。
